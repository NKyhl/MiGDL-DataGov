Projection Table Inventory & Grain Analysis

Projection layer tables are loaded append-only, so they miss upstream updates and deletes. This page analyzes how each derived and platinum table is built today and proposes how to keep it correct as silver and gold main change.

Current State

Properties of the existing SQL

1. Append-only loads

Derived tables load with INSERT … LEFT JOIN target ON <natural key> WHERE target.<key> IS NULL. The one exception is dim_education_organization, which is deleted and rebuilt.

2. Latest-row dedup

ROW_NUMBER() keeps the most recently updated row per natural key, often partitioned on slightly different columns than the insert guard uses.

3. Inconsistent student identity

Student IDs are resolved with OR conditions in joins, in different orders across tables. This risks fan-out and mismatches.

4. Volatile keys

migdl_ key columns embed ingestionbatchid and ingestiontimestamp, so they change and should not be used for matching.

5. No current-row filter on conf reads

currentflag = TRUE is commented out in the SQL of 13 of the 22 derived tables (for example dim_staff, dim_student and fact_grade), so expired SCD2 versions can feed derived tables.

6. Whole district-year rescans

Each derived statement is parameterized only by district and year. Nothing narrows it to a batch or a set of keys, so a run evaluates every row for the district and year, and cost follows population, not changes.

7. Per-statement commits

The runner commits after each statement and rolls back only the one that fails, so an error partway through a table leaves the earlier statements committed and the table partly written.

8. Derived tables depend on each other

15 of the 22 read another derived table, such as dim_education_organization, dim_student and fact_student_enrollment. Run order matters (G5 notes that dim_grade_type loads after fact_grade, which depends on it), and dim_student and fact_student_program read each other.

9. Child fan-out collapsed arbitrarily

Where conf holds one row per child combination, derived keeps one row per key, as in dim_staff, dim_parent, dim_student and fact_discipline_action. The pick is the latest updatetimestamp, with ties arbitrary, so the values on the other rows are lost.

What that means for delta correctness

ScenarioEffect today
First load for a keyThe row is inserted.
An update upstream for an existing keyThe row is dropped: the key already exists in the target.
A hard delete upstreamThe derived row stays current.
A child-only change in silver (e.g. a new email)Conf is updated, but the derived row keeps the old values.
A joined table changes (e.g. a school name)The derived columns stay stale.
Expired conf versionsDerived tables without a currentflag = TRUE filter can read them as current.

Key Solution Requirements

FindingRequirement
Mechanism: No update or delete branchesWe need to add branches that apply updates and deletes.
Grain: Child data is lost and chosen arbitrarilyWe need a deterministic way to fan in or drop child data.
Grain: Inconsistent natural key usageWe need to decide on keys per table and use them consistently.
Joins: Many source tables can cause a single derived row to need recomputingWe need to define what causes dirty keys for each table.
Ordering: There are derived-to-derived dependenciesWe need an appropriate order when loading.
Inactive data: Many tables do not filter conf by currentflag = TRUEWe need to add currentflag filters.

G5 Strategies

Note: Assumes G1–G4 are implemented: silver applies every upstream change, including deletes, and gold main (the conf tables) applies each one as a record-level replacement, with batch ids, a record flag and tombstones.

Update and Delete Mechanisms

For each derived table the analysis records its grain and driving key, upstream sources, build shape, how child data is handled, and a candidate strategy. The strategies under consideration:

1. Recompute

Delete and rebuild the slice. Simple and always correct, but it rewrites everything.

2. Dirty-key upsert: MERGE

Update or insert only the changed keys. Fits tables that map 1:1 to their conf grain.

3. Dirty-key upsert: key-slice-replace

Delete and re-insert every row for a changed key. Fits tables where the row count per key can change (1:N or N:N).

4. Retire

Remove the table completely, or move its logic into existing ETL.

Two cross-cutting points: most derived tables draw from several source tables, so dirty keys have to be detected across more than one source; and choosing recompute for a table makes it harder to propagate deletes beyond that table.
