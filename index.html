Gold Derived Delta Correctness Analysis

Gold derived tables are loaded append-only, so they miss upstream updates and deletes. This page analyzes how each derived table is built today and proposes how to keep it correct as silver and gold main change. Assumes G1–G4 are implemented.

Current State

Properties of the Existing ETL

1. Append-only loads

Derived tables load with INSERT … LEFT JOIN target ON <natural key> WHERE target.<key> IS NULL. There are a few exceptions, but they are not complete: 1) dim_education_organization is deleted and rebuilt. 2) dim_student and fact_student_enrollment run additional SQL UPDATE passes to update some columns.

2. Child fan-out collapsed arbitrarily

While gold main holds one row per silver child combination, derived tables keep one row per key. One gold main row is picked using latest updatetimestamp, but that is equal across child fan-out rows. The outcome is that one gold main row is picked arbitrarily while all other child combinations are lost. Derived tables that do not read any child columns from gold main do not experience data loss, but performance improvements could be made to prevent extracting and joining all conf child combinations.

3. Not all child columns are used

Gold main fans out by child tables, but derived reads only some of them, and for some tables none (for example, none of the four child tables behind dim_student_conf, and 4 of the 18 behind dim_staff_conf). A change to an unread child column does not change the derived row.

4. Frequent, complex joins

The derived layer is built from more frequent and more complex joins. A change or delete in any joined table can change or remove a derived row, so updates and deletes cannot be propagated from one source table alone.

5. Derived tables depend on each other

15 of the 22 derived tables read another derived table, such as dim_education_organization, dim_student and fact_student_enrollment. Run order matters. Outliers: 1) fact_grade joins dim_grade_type but is sequenced after, and 2) dim_student and fact_student_program read each other.

6. No current-row filter on conf reads

currentflag = TRUE is commented out in the SQL of 13 of the 22 derived tables (for example dim_staff, dim_student and fact_grade), so expired SCD2 versions and TYPE1 delete tombstones can feed derived tables.

7. Per-statement commits

The runner commits after each statement and rolls back only the one that fails, so an error partway through a table's SQL statements leaves the earlier statements committed and the table partly written. Today, this only matters for tables with several statements (dim_student, dim_education_organization, and fact_student_enrollment).

8. Inconsistent natural key usage

ROW_NUMBER() dedups are used to keep the most recently updated conf row per key, but some dedups are partitioned on a different set of columns from the append-only guard (assumed natural key). The two can disagree about which rows count as the same.

9. Inconsistent student identity

Student IDs are resolved with OR conditions in joins, in different orders across tables. This risks fan-out and mismatches.

10. Volatile keys

migdl_ key columns embed ingestionbatchid and ingestiontimestamp, so they change and should not be used for matching.

11. Whole district-year rescans

Each derived statement is parameterized only by district and year. Nothing narrows it to a batch or a set of keys, so a run evaluates every row for the district and year, and cost follows population, not changes.

Suggested Approach

The issues noted above do not all need to be solved at once. In our first pass, we can solve all blocking issues for update and delete propagation for data at the parent level, which will greatly improve the experience for MiGDL school districts.

Later we can revisit how child grain is represented and maintained in the gold and platinum layers, which may involve significant engineering for a smaller correctness impact and may be included in a broader re-architecture of the Redshift layers.

Solution Design

This section describes how we propose to solve the properties marked Solve above. Each subsection lists the properties it addresses.

1. Keys and Identity Properties 8, 9, 10

A change is tracked with three keys. The conf key is the silver natural key, which identifies a parent record and is shared by every fanned-out row for it. A dirty key is a conf key whose data changed, either in the table's own conf table or in a table it joins. A derived key identifies one row in the derived table. A dirty key maps to one derived key or to several.

Real keys from the SQL, assuming one conf row per key. District and year are part of every key and are left out. A dirty key is a conf key from the left, and it covers the derived keys it maps to on the right: one each for the discipline incident and student, and one per school for staff.

  • Each table defines one derived key and uses it for the dedup, the existence check and the dirty-key mapping. Today these can disagree.
  • Every table that joins students uses one definition of a student.
  • No key uses the migdl_ columns, because they change with every ingestion. Surrogate keys are built deterministically from natural key parts, so a delete and rebuild does not change them. We could consider removing the migdl_ columns.
  • Gold key columns must equal the silver natural keys. A delete tombstone carries only silver's keys, so a gap means deletes silently do nothing for that table.

2. Gold Main Extract Properties 4, 6, 11

Gold derived reads what gold main records about each change. Every conf table carries recordflag (IU or D), ingestionbatchid and currentflag, and a delete leaves one tombstone row per delete event. Finding the dirty keys for a table:

  1. Keep a watermark per district: the latest gold main batch already refreshed into derived.
  2. For every source the table reads, take the conf keys with rows in batches after the watermark. Fanned-out rows share a key and a batch id, so a parent counts once.
  3. A key with a current row is changed. A key with a tombstone and no current row is deleted. A key that was deleted and re-created counts as changed, because the current row wins.
  4. For a joined table, map its changed keys back through the join to this table's keys. A change in a table that many tables read dirties all of them.
  5. Recompute from current rows only (currentflag = TRUE), so tombstones and expired versions never reach derived. 13 of the 22 derived tables comment this filter out today.

Only rows after the watermark count. B has a tombstone and no current row, so it is deleted.

A change to a child row re-versions its parent in silver, so the key is dirty even when derived never reads that child column (property 3). Unchanged re-sends do not reach staging, because silver treats them as no-ops, so they should not create dirty keys. Refreshing only dirty keys, instead of scanning the whole district and year, addresses property 11.

3. Refresh Strategy Properties 1, 7

A refresh strategy is how one derived table is brought up to date for its dirty keys. It is defined per table, from the table's derived grain and from how a dirty key maps to its derived keys. The Gold Derived Inventory below records the candidate for each table.

StrategyFitsOn updateOn deleteCost

MERGEEach dirty key maps to exactly one derived key, and the mapping is stable.The matching row is updated, and a new key is inserted.Needs an explicit delete branch for keys with no current rows.The source must have at most one row per derived key.
Key-slice-replaceA dirty key maps to several derived keys, or to a set that can change between runs.The key's rows are deleted and the recomputed rows inserted.The key's rows are deleted and nothing is inserted.More rows are rewritten than with MERGE. Deleted rows stay until VACUUM.
  • Choosing: MERGE fits when a key's derived rows are fixed. Key-slice-replace fits when they can appear or disappear. Recompute is the fallback where a partial refresh is impractical.
  • Default: gold main chose one expire-and-insert template for every entity, over MERGE for the entities where MERGE could apply, to keep one pattern to build and validate. The same reasoning could favour key-slice-replace as the default for derived, with MERGE as an optimization. This is open.
  • Atomic: each refresh, delete and insert together, runs in one transaction, so a failure cannot leave a table partly written. It reuses the orchestrator transaction support that gold main also needs.
  • Rebuild: Recompute is also the rebuild path. A derived-only rebuild of derived and platinum from intact gold main is routine and history-safe, and a rebuild of gold main itself must be followed by one.
  • Retire, removing a table or moving its logic into existing ETL, is a per-table decision, not a refresh strategy.

4. Delete Handling Properties 1, 6

A delete is the case an append-only load misses entirely. This is its path from silver to gold derived.

  1. Silver records the delete as a tombstone with the natural keys and the delete's batch id.
  2. Gold main widens its extract to include the tombstone. It then expires the key's rows (SCD2: currentflag false and effectiveto set) or hard-deletes them (TYPE1 and INCREMENTAL), and inserts one tombstone row with recordflag = D.
  3. The extract in section 2 finds a key after the watermark with a tombstone and no current row, so the key is deleted.
  4. The refresh recomputes from current rows only and finds none, so the key's derived rows are removed. Recompute and key-slice-replace do this by construction. MERGE needs its explicit delete branch.
  5. Tables that read this table treat the key as dirty, so the delete cascades along the dependency graph in section 5.

A delete only reaches derived if reads exclude tombstones, which is why the current-row filter in section 2 is a prerequisite. A key that is deleted and then re-created ends current, because the current row wins over the earlier tombstone.

5. Order and Dependencies Property 5

15 of the 22 derived tables read another derived table, so a table must refresh after the tables it reads, and its dirty keys come from them. The graph shows each table's reads, taken from the SQL. Hover a table to trace what it reads and what reads it.

Each column is one layer of a topological sort. Tables in a layer can load in any order, and every layer follows the one before it. The small number is the table's position in today's run.

Load order is that topological sort. Today's order is already valid except in two places:

  • fact_grade reads dim_grade_type but loads one position before it. dim_grade_type reads no other derived table, so it can move ahead of fact_grade.
  • dim_student and fact_student_program read each other, which looks like a cycle between tables. It is not a cycle between statements: dim_student's insert and flag passes 2 to 6 read no derived table, and its passes 7 to 16 read fact_student_program. Splitting dim_student into those two nodes, as in the graph, removes the cycle.

Dirty keys follow the same edges: a changed key in a table dirties the keys that read it. dim_student, dim_education_organization and dim_school_year have the most readers (12, 11 and 10), so a change to them reaches the most tables.

6. Open Items

  • Child fan-out: child attributes are still picked arbitrarily, and a child-only change may or may not reach the derived row, until we decide how child grain is represented (properties 2 and 3).
  • Platinum: not covered. It reads gold derived and gold main, so it needs the same dirty-key step carried one hop further. A derived-only rebuild already includes platinum. Per-table platinum strategies are open.
  • Watermark: where it is stored per district, and whether the gold extract identifies unprocessed batches by a high-water mark or by a registry of batches.
  • Default strategy: per table, or one template for all of gold derived (section 3).
  • Gold main prerequisites: the record flag, transaction support and the pilot must land first. This design assumes them.
  • dim_student flag passes: tables that run after its passes 7 to 16 also see the final flags. Whether any of them needs those flags is not checked.
  • DynamoDB-facing views: part of the wider G5 design, not analyzed here.
