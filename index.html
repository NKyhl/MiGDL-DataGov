Gold Derived Delta Correctness Analysis

Gold derived tables are loaded append-only, so they miss upstream updates and deletes. This page analyzes how each derived table is built today and proposes how to keep it correct as silver and gold main change. Assumes G1–G4 are implemented.

Current State

Table Inventory

All 22 gold derived tables are listed below, along with their current driving key and build shape. Every table has a page, linked on the right. Notes pages hold basic analysis and notes gathered from Tiger Team 3 discussion thus far. Walkthrough pages additionally include visualizations for helping readers understand build shape, grain, known consumers, etc.

Properties of the Existing ETL

1. Append-only loads

Derived tables load with INSERT … LEFT JOIN target ON <natural key> WHERE target.<key> IS NULL. There are a few exceptions, but they are only partial solutions: 1) dim_student and fact_student_enrollment run additional SQL UPDATE passes to update some columns. 2) dim_education_organization is deleted and rebuilt.

2. Child fan-out collapsed arbitrarily

While gold main holds one row per silver child combination, derived tables keep one row per key. Derived ETL chooses one gold main row, using latest updatetimestamp to pick, but we know that updatetimestamp is equal across child fan-out rows. The outcome is that one gold main row is picked arbitrarily while all other child combinations are lost. Some derived tables do not read any child columns from gold main, and in that case do not experience data loss, but they still experience worsened performance due to extracting and joining all conf child combinations before the dedup.

3. Not all gold main child columns are used

Gold main fans out by child tables, but derived does not read all of these columns. Some derived tables select no child columns from their gold main source table. Examples: none of the four child tables behind dim_student_conf are selected by dim_student, and 4 of the 18 behind dim_staff_conf are not selected by dim_staff. This means that a change to a child column in gold main does not necessarily change the derived row. It also means that our silver to gold fan-out is not required to serve the derived layer for some entities.

4. Frequent, complex joins

The derived layer is built from more frequent and more complex joins. A change or delete in any joined table can change or remove a derived row, so updates and deletes cannot be detected from one source table alone.

5. Derived tables depend on each other

15 of the 22 derived tables read another derived table, such as dim_education_organization, dim_student and fact_student_enrollment. Run order matters. Outliers: 1) fact_grade joins dim_grade_type but is sequenced after, and 2) dim_student and fact_student_program read each other.

6. No current-row filter on conf reads

currentflag = TRUE is commented out in the SQL of 13 of the 22 derived tables (for example dim_staff, dim_student and fact_grade), so SCD2 expired rows and TYPE1 delete tombstones can feed derived tables.

7. Per-statement commits

The runner commits after each SQL statement and rolls back only the one that fails, so an error partway through a table's SQL statements leaves the earlier statements committed and the table partly written. Today, this only matters for tables with several statements (dim_student, dim_education_organization, and fact_student_enrollment).

8. Inconsistent natural key usage

ROW_NUMBER() dedups are used to keep the most recently updated conf row per key, but some dedups are partitioned on a different set of columns than the append-only guard (assumed natural key). The two can disagree about which rows count as the same.

9. Inconsistent student identity

Students have both a district student id (student_unique_id) and a state_student_id, and tables match on either one with OR conditions, in different orders. dim_student alone uses four formulas to decide which student a row is. With no single id as the identity, the same student can resolve differently from table to table, joins could fan out or mismatch, and dim_student has no well-defined key for a refresh to target.

10. Volatile keys

Some keys are hashed from ingestionbatchid and ingestiontimestamp, so a row gets a new key every time it is re-ingested. Most of these keys are never used. The exceptions are school_year_key and grade_type_key, which facts store as foreign keys. If we rebuild those two tables, the stored keys no longer match anything. staff_key and student_key are hashed from a derived id, so they change if that id changes.

11. Whole district-year rescans

Each derived statement is parameterized only by district and year. Nothing narrows it to a batch or a set of keys, so the gold main extract evaluates every row for the district and year, and ETL cost is determined by the gold main population size, not the delta size.

Suggested Approach

The issues noted above do not all need to be solved at once. In our first pass, we can solve all blocking issues for update and delete propagation for data at the parent level, which will greatly improve the experience for MiGDL school districts.

Later we can revisit how child grain is represented and maintained in the gold and platinum layers, which may involve significant engineering for a smaller correctness impact and may be included in a broader re-architecture of the Redshift layers.

Solution Design DRAFT

This section describes how we propose to solve the properties marked Solve above. Each subsection lists the properties it addresses.

1. Keys and Identity Properties 8, 9, 10

Natural Key Usage Property 8

Every delta strategy matches rows on a key: to decide whether a row already exists, to dedup, to find the rows that need recomputing, and to join one derived table to another. When a table's keys are inconsistent, a refresh can miss rows, insert duplicates or touch the wrong ones. So the first step to delta correctness is to define the keys for each derived table and use them consistently.

Current State Analysis

Today, most derived tables use different columns for their dedup, their insert guard and their surrogate key. We found five kinds of mismatch in 16 of the 22 tables:

  • the dedup and the insert guard use different columns (fact_grade dedups on 8 columns and guards on 6)
  • the school year is missing from one side
  • a nullable key column is compared with =, so the same row can be inserted again on every run
  • a surrogate key hashes parts the guard ignores
  • a surrogate key is not unique (education_org_key omits district and year)

Proposed Solution

We propose new natural keys for two tables, listed first below. Then, we propose corrections to 14 other tables which have inconsistent keys across insert guards, dedups, surrogate keys, etc.

Proposed Key Consistency Fixes

Volatile Keys Property 10

Current State Analysis

Volatile keys are keys that are generated with ingestionbatchid or ingestiontimestamp embedded in their hash. Because those fields change when a gold main row is recomputed (exists today) or reversioned on update (after G3/G4 implementation), these keys are not stable enough to be used for matching in ETL, as the source for determining if a key is dirty, or for JOINs.

Today, most of these volatile keys are not read at all, so there is little to no impact. However, there are two gold derived keys that are used as foreign keys in other tables, and a rebuild of the source table would leave those stored values pointing at nothing.

Two other keys, staff_key and student_key, are not volatile, but they hash a derived id instead of the raw one, so they change when that id does. They are stored as foreign keys, so they carry the same risk when rows are recomputed.

2. Order and Dependencies Property 5

The next step to achieving a gold derived delta correctness solution is to understand the table-to-table dependencies that exist within the layer. 15 of the 22 derived tables read another derived table, so a table must refresh after the tables it reads, and its dirty keys must come from them.

Table Dependency Analysis

The graph below shows the read dependencies between gold derived tables today, taken from the SQL. Each table shows its sequence number(s) in the load order today (“#N”, or a range when a table has several steps). Some tables have a colored dot, which corresponds to a specific note below the visual. Hover over a table to trace what it reads and what reads it.

Each column is one layer of a topological sort. Tables in a layer can load in any order, and every layer follows the one before it. Where a table has several steps in the current state, the "today" range shows all of them. Boxes with a dotted border are temp-table staging steps (#36 to #38 and #40) that feed gold derived tables. There are additional staging table steps that are only read by platinum (#41 to #47), but these are not shown above.

Load order is that topological sort. Today's order is already valid except in two places:

  1. fact_grade reads dim_grade_type but loads one position before it. dim_grade_type reads no other derived table, so it can move ahead of fact_grade. Both are marked with an orange circle in the graph.
  2. dim_student and fact_student_program read each other, which looks like a cycle between tables. It is not a cycle between statements: dim_student's insert and flag passes 2 to 6 read no derived table, and its passes 7 to 16 read fact_student_program. Splitting dim_student into those two nodes, as in the graph, removes the cycle. Both dim_student nodes and fact_student_program are marked with a teal circle in the graph.

There are also two tables which share a step today (and SQL file). We can separate these:

dim_staff and dim_parent load in one step today (#10) because dim_staff.sql includes SQL to build both tables. There is no dependency between the tables, and we propose splitting them into two steps, in separate SQL files.

Separately, the gold derived load also builds staging temp tables, which exist only during the gold derived connection. Some are necessary, and others are wasted compute:

  1. TEMP table steps #41–#47 are never used in derived and should be removed (not shown). These steps in today's gold derived load build staging temp tables that gold derived does not use, so that compute is wasted. The same steps already run again in the platinum layer load, where they are needed. Additionally, stg_miread_foa_join (step #47) reads fact_student_objective_assessment (step #48), which is out of order. We should remove all of these steps from gold_derived.yaml.
  2. TEMP table steps #36–#38 and #40 are used in derived and built again in platinum. These staging tables are used by gold derived. They feed fact_student_assessment (#39) and fact_student_objective_assessment (#48), and they are shown in the graph with dotted borders and a blue circle. However, they only live during the life of the transaction. Platinum needs them too, and its load builds them again. We could consider making these tables persistent so we do not build them twice.

Dirty keys should follow the same edges: a changed key in one table dirties the keys that read it. dim_student, dim_education_organization and dim_school_year have the most readers (12, 11 and 10, respectively), so a change to them reaches the most tables.

Proposed Solution

Move dim_grade_type ahead of fact_grade, split dim_staff and dim_parent into separate steps, and remove steps #41 through #47 from the gold derived load. The rest of the order is valid. dim_student stays in two parts until the open item below is resolved. In the proposed order, each entity has one SQL file with several statements, so each entity gets one number in our proposed solution.

3. Gold Main Extract Properties 4, 6, 11

⚠
This section is in progress! Content is hidden for now.

A dirty-key refresh needs to know which keys changed in gold main since derived last ran. Gold main records this on every conf row: ingestionbatchid, currentflag and recordflag (IU or D). A delete leaves a tombstone row. This assumes G3 and G4. MERGE and key-slice-replace both use this extract. Recompute does not need it.

  1. Fix the batch list. At the start of a run, take the gold main batches for the district and year that derived has not refreshed yet. Use the same list for every table in the run, so all tables see one consistent window.
  2. Find the changed keys in each source. For every gold main table a derived table reads, take the keys that have a current row (currentflag = TRUE) with a batch id in the list. Gold main keeps several rows per record when children fan out, and they share one key and one batch id, so a record counts once.
  3. Find the deleted keys. Take the keys that have a tombstone (recordflag = 'D') in the list and no current row. A key can have more than one tombstone over time, so take the distinct keys. You do not need the latest one. If a key has a current row, it is changed, because gold main only leaves a current row when it is newer than the tombstone.
  4. Map them to derived keys. Each source's keys map to this table's keys through its join. A change in a table that many rows read, such as a school name, dirties all of them. Dirty keys from an upstream derived table are added once that table has refreshed, so they follow the load order.
  5. Recompute from current rows. For every dirty key, read all of its current rows, not only the rows in the batch list. 13 of the 22 derived tables comment out the currentflag = TRUE filter today, so tombstones and expired versions can reach derived.
  6. Mark the batches. After the whole run succeeds, record that the batches have been refreshed into derived.

Batches 5 and 6 have not been refreshed yet. A and C have current rows in them, so they are changed. B has a tombstone and no current row, so it is deleted. D last changed in batch 3, which derived already refreshed, so it is skipped.

What each strategy does with the dirty keys. MERGE upserts the keys that still have rows and deletes the dirty keys that have none, in one transaction. Key-slice-replace deletes the key's rows and inserts the recomputed ones, so a deleted key just inserts nothing.

Tracking the batches. The ingestion tracker already records GOLD MAIN LOAD COMPLETED for each batch, and gold main uses it to find the batches it has not processed. It does not record whether derived has consumed a batch. Derived runs after gold main, so if derived fails, the next run would see those batches as done and lose its window. Derived needs its own per-batch status, written only after the run succeeds. A set of unprocessed batches also survives a failed run in the middle, which a single watermark would not.

A change to a child row re-versions its parent in silver, so the key is dirty even when derived never reads that child column (property 3). For TYPE1 and INCREMENTAL tables, an unchanged re-send still advances the batch id, so some keys look dirty without a real change. That costs compute, not correctness. Refreshing only dirty keys, instead of scanning the whole district and year, addresses property 11.

Open items:

  • Derived batch status: whether derived records its progress as a new per-batch status in the ingestion tracker or as a separate watermark, and what to call it.
  • Tracker writes: whether two jobs can safely write the tracker file, which is a CSV in S3.
  • Tombstone ordering: step 3 relies on gold main never leaving a current row that is older than a tombstone for the same key. We have not checked that against the data.

4. Refresh Strategy Properties 1, 7

A refresh strategy is how one derived table is brought up to date for its dirty keys. It is defined per table, from the table's derived grain and from how a dirty key maps to its derived keys. The Solution by Table section below records the candidate for each table.

StrategyFitsOn updateOn deleteCost
RecomputeAny grain.The whole district-year slice is deleted and rebuilt.The rebuilt slice no longer contains the key.Every row is rewritten, changed or not. Deleted rows stay until VACUUM.
MERGEEach dirty key maps to exactly one derived key, and the mapping is stable.The matching row is updated, and a new key is inserted.Needs an explicit delete branch for keys with no current rows.The source must have at most one row per derived key.
Key-slice-replaceA dirty key maps to several derived keys, or to a set that can change between runs.The key's rows are deleted and the recomputed rows inserted.The key's rows are deleted and nothing is inserted.More rows are rewritten than with MERGE. Deleted rows stay until VACUUM.
  • Choosing: MERGE fits when a key's derived rows are fixed. Key-slice-replace fits when they can appear or disappear. Recompute is the fallback where a partial refresh is impractical.
  • Default: gold main chose one expire-and-insert template for every entity, over MERGE for the entities where MERGE could apply, to keep one pattern to build and validate. The same reasoning could favour key-slice-replace as the default for derived, with MERGE as an optimization.
  • Atomic: each refresh, delete and insert together, runs in one transaction, so a failure cannot leave a table partly written. It reuses the orchestrator transaction support that gold main also needs.
  • Rebuild: Recompute is also the rebuild path. A derived-only rebuild of derived and platinum from intact gold main is routine and history-safe, and a rebuild of gold main itself must be followed by one.
  • Retire, removing a table or moving its logic into existing ETL, is a per-table decision, not a refresh strategy.

Open items:

  • Default mechanism: whether derived uses one template for every table (key-slice-replace, with MERGE as an optimization) or a small set chosen per table.

5. Delete Handling Properties 1, 6

⚠
This section is in progress! Content is hidden for now.

A delete is the case an append-only load misses entirely. This is its path from silver to gold derived.

  1. Silver records the delete as a tombstone with the natural keys and the delete's batch id.
  2. Gold main widens its extract to include the tombstone. It then expires the key's rows (SCD2: currentflag false and effectiveto set) or hard-deletes them (TYPE1 and INCREMENTAL), and inserts one tombstone row with recordflag = D.
  3. The extract in section 3 finds a key after the watermark with a tombstone and no current row, so the key is deleted.
  4. The refresh recomputes from current rows only and finds none, so the key's derived rows are removed. Recompute and key-slice-replace do this by construction. MERGE needs its explicit delete branch.
  5. Tables that read this table treat the key as dirty, so the delete cascades along the dependency graph in section 2.

A delete only reaches derived if reads exclude tombstones, which is why the current-row filter in section 3 is a prerequisite. A key that is deleted and then re-created ends current, because the current row wins over the earlier tombstone.

6. Further Analysis

  • Child fan-out: child attributes are still picked arbitrarily, and a child-only change may or may not reach the derived row, until we decide how child grain is represented (properties 2 and 3).
  • Platinum: not covered. It reads gold derived and gold main, so it needs the same dirty-key step carried one hop further. A derived-only rebuild already includes platinum. Per-table platinum strategies are open.
  • DynamoDB-facing views: part of the wider G5 design, not analyzed here.
