Platinum Current State AnalysisDRAFT

The platinum layer builds the MiRead, EWIMS, roster and student-detail products from gold. This page analyzes how each of its 18 tables is built today and what it would take to keep them correct as gold changes. It follows the structure of the gold derived analysis and assumes the same upstream fixes (G1–G4) and gold derived work. Everything here comes from the SQL and the repository; no data was checked.

Current State

Table Inventory

All 18 platinum tables, with their current driving key, build shape and consumers. The write pattern shows how a table is loaded today: seed dimensions and most facts insert a key once, four curated tables are written with MERGE, and the EWIMS curated table is rebuilt by a PySpark step. Which platinum tables read each gold derived table is shown in the Consumers row of each table page on the gold derived page; the dependencies between platinum tables are in Solution Design below.

* Consumers are the layers that read a table directly: another platinum table or one of its staging tables (PLAT), or the API, which includes the DynamoDB publishers (API). NONE means nothing reads the table. Hover a tag to see which readers.

Properties of the Existing ETL

1. Insert-once loads, with a few UPDATE passes

Dimensions and facts load with INSERT … LEFT JOIN target … WHERE target.<key> IS NULL (or NOT EXISTS), so a key that already exists is never rewritten. Three facts then run UPDATE passes that overwrite some columns: fact_ewims_student_early_warning (grade statuses and composites), fact_miread_student_assessment (component pivot) and fact_miread_student_assessment_component (component code backfill). Four curated tables use MERGE, which updates matched rows but has no delete branch. Only the EWIMS curated table removes rows that disappeared upstream, because it deletes and reloads its district-year.

2. Staging is rebuilt in full, then filtered by the guard

The 13 prerequisite temp tables and the staging and tmp_* tables inside the load are dropped and recreated for every district-year. The facts they feed insert only keys that are missing, so the work spent recomputing values for existing keys is discarded. The header of stg_edfi_component_src describes its build as a 20 to 30 minute step.

3. Platinum reads both gold derived and gold conf

Most inputs are gold derived tables such as dim_student, dim_staff and fact_student_enrollment. Some steps read conf directly: the Acadience component insert reads fact_student_assessment_conf, EWIMS reads fact_grade_conf and fact_student_school_attendance_conf, and the curated discipline staging reads fact_discipline_incident_conf. A fix in gold derived does not reach those inputs, and a conf delete can reach platinum without passing through derived.

4. Platinum tables depend on each other and on staging

7 of the 11 facts and curated tables read another platinum table, directly or through staging. The MiRead chain is a loop at the table level: the assessment fact feeds the component fact, which feeds a rollup that updates the assessment fact. Load order is the order of the manifest, with prerequisites run first. At least two prerequisites read a dimension that is built after them (see Order and Dependencies).

5. Guards and keys do not match the columns written

Some inserts write a state student or staff id into the student_unique_id or staff_unique_id column, while the guard compares that column to the local id. This is the case for fact_teacher_roster and fact_miread_student_assessment. Where the two ids differ, the guard could fail to match and the row could be inserted again on every run (not checked in data). In fact_miread_student_assessment the two id columns are written swapped: student_unique_id holds the state id and district_student_id holds the local id. The curated discipline key uses the state id in a column also named student_unique_id.

6. MERGE keys include columns that change

curated_district_roster and curated_enrollment_history match on dates and a teacher id in addition to the entity keys. If an entry date, exit date or session date changes, the row no longer matches, so the changed row is inserted and the old one stays. curated_enrollment_history and curated_student_discipline compute the match hash on the target table in the ON clause. curated_miread_district_assessment matches on district, school, year and student_assessment_identifier alone, with no student or assessment. In curated_enrollment_history, the update sets student_section_end_date from student_section_begin_date, which looks like a copy error.

7. Seed dimensions are loaded once and are not scoped

The six seed dimensions are built from hardcoded rows. Each insert has a guard on the code columns, so a changed seed value is never applied. Their keys are MD5(code | GETDATE()), so a key differs every time a row is inserted, and the component fact stores these keys. The cross join over maisa_school_districts is not limited to the district being processed, so the first run for any mi_read or mi_ewims district seeds rows for all of them. dim_ewims_status_threshold has no writer, and nothing reads the two EWIMS dimensions that are built.

8. Run-date and snapshot columns

fact_miread_student_context stores snapshot_date = CURRENT_DATE with attendance, discipline and contact totals. Because the table is insert-once, those values are frozen at the first run for each student, school and year. fact_teacher_roster.is_current_enrollment and the primary-teacher filter in the context staging use CURRENT_DATE, so the same inputs give a different result on a different day.

9. Reads are not scoped to the district-year, and years depend on each other

Several staging queries read every district or every year: stg_ewims_grade_by_period reads all of fact_grade_conf for every mi_ewims district, the second EWIMS update pass covers every mi_ewims district for the year, the third is limited to neither district nor year, and the discipline aggregates in the curated staging have no district or year filter. The context and enriched tables use all years for retentions and for the history timeline (school_year <= {schlyear}, and a join on student_key alone), so a change in one year affects rows of other years.

10. Nested JSON built by string concatenation

The support-team, discipline, retention, assessments and history JSON are assembled with LISTAGG and string concatenation, capped by rn <= N and, for the support team, cut with LEFT(…, 2000). The quote escaping is written as REPLACE(x, '"', '"'), which as written replaces a quote with itself. A long value could be cut mid-object and a name containing a quote could produce invalid JSON (not checked in data).

11. Per-statement commits and two engines

The runner commits after each statement, and the prerequisites commit one at a time. The EWIMS curated table is built afterward by a PySpark step that is called from main.py and is not in the manifest, in its own transaction. A failure partway leaves earlier statements committed, and the district-year is marked PLATINUM LOAD FAILED as a whole. Session temp tables such as #pt_ctx_sd1 exist only for the one connection used for the district-year.

1. Order and Dependencies Property 4

A platinum table must load after the platinum tables and staging tables it reads, and a change to a table reaches everything downstream of it. Platinum reads gold derived tables as well, and those must be loaded first, as they are today.

Each column is one layer of a topological sort. Tables in a layer can load in any order, and every layer follows the one before it. Gold derived inputs are not drawn. No table in one product (MiRead, EWIMS, roster, student detail) reads a table in another product.

The order today is valid except in the places below. Each note is marked with a colored dot in the graph.

  1. stg_miread_component_patterns and stg_miread_component_key are prerequisites, so they run before step #0, but both read dim_miread_literacy_component, which step #0 writes. On the first run for an environment the dimension is still empty when they build, so the component mapping would be empty for that run. After that they read rows seeded by an earlier run. The six seed dimensions read only maisa_school_districts, so they can load first.
  2. fact_miread_student_assessment is read by the component fact, whose rollup then updates it, which looks like a cycle between tables. It is not a cycle between statements: the insert (#13) reads no component data, and the rollup update (#20) reads the component fact. Splitting the table into two nodes, as in the graph, removes the cycle. It also shows that only stg_miread_district_assessment needs the update: pt_ctx_sd1, tmp_assessments_json and the component staging read only columns written at insert.
  3. stg_edfi_assessment_base, stg_edfi_assessment_scores, stg_migdl_parent_assessments and stg_migdl_objective_assessments are also built in the gold derived load, where they feed fact_student_assessment and fact_student_objective_assessment. Platinum builds them again, because they only live for the connection. Marked with a blue dot.
  4. stg_nwea_performance_level_lookup has no reader in the platinum SQL, so its build is wasted compute. The two EWIMS dimensions also have no readers. noop_018.sql and diagnostic_022.sql are skipped by the runner and can be removed from the manifest.

Smaller notes: tmp_enrollments_json begins by dropping tmp_components_json, which is harmless today only because tmp_assessments_json has already read it. The EWIMS curated step is hardcoded in main.py after all SQL, so it is outside the manifest and its position relative to the fact is not visible there. dim_ewims_status_threshold is not in the graph because nothing writes or reads it.

Dirty keys should follow the same edges. fact_miread_student_assessment and its component fact have the most readers, so a change to them reaches the most tables: the context chain, both MiRead curated tables and the rollup.

Proposed Solution

Load the six seed dimensions first, so the two component prerequisites always read a built dimension. Group the rest by product, which is possible because no product reads another. Give each table one position, with multi-statement tables as one entry (fact_miread_student_assessment keeps two because of the split above). Remove the staging table with no reader and the two entries that never run.

Open items:

  • Where do prerequisites run? They run up front today. Placing each staging table beside its consumer (as proposed) shortens how long it holds session memory, but the temp tables stg_* that gold derived also builds could instead become permanent tables, the same open item as on the gold derived page.
  • Should the EWIMS Spark step be a manifest entry? It runs after all SQL from main.py and in its own transaction. Putting it in the manifest would make its dependency on fact_ewims_student_early_warning visible and let a district-year run one product at a time.
  • Do the two EWIMS dimensions and dim_ewims_status_threshold have consumers? Nothing in this repository reads the first two, and nothing writes the third. Open: whether anything outside the lake and API uses them, or whether they should be retired.
  • Do the platinum facts have consumers beyond the curated tables? Not through the live routes. The routers call only the v2 handlers, which read the curated tables, and fact_miread_student_context_enriched for /miread/student/context. The Redshift grants for the API roles match this. The older handlers (roster.py, roster_v1.py, district_assessment.py, student_context_v2.py) read fact_teacher_roster and the MiRead facts but are not routed, and the API spec (2.2.2) still describes some routes as returning columns from those facts. Open: whether anything outside this repository reads the facts directly, and whether the unused handlers and the stale spec text should be removed.
